# AutoGit

**中文菜单式 Git 助手：选一个任务，按提示完成，不用记一串 Git 和 SSH 命令。**

专注下载、基础保存与上传、远程管理和 GitHub 协作，适合不想反复配置账号和密钥的使用者。支持多账号、项目独立身份、加密凭据、远端强推与删除、服务端 PR 合并和发布管理；本版有意移除高级本地 Git 操作，不再提供本地分支/合并、stash、reset/clean 或冲突恢复向导。

当前版本号 **0.5.0**，使用 **TypeScript / Node.js**，每次启动用**独立的 AutoGit 解锁密码**打开加密凭据库。Linux / Windows 均可用普通用户权限安装和使用，**不需要 Python、运行时 npm 依赖、系统密码、PAM 策略或管理员配置**。密钥生成/导入、会话 SSH agent 和 Windows 文件权限保护依赖随包提供的原生助手，不能只复制 JavaScript。详细范围与实测边界见 [功能与缺口台账](docs/capabilities.md)。

> **实现与验收分开**：独立密码不是操作系统登录，也不是 GitHub 登录。须使用包含匹配平台原生密钥/权限助手及完整性清单的发行包；缺失或校验失败时，对应操作会停止，不降级保存明文私钥。新流程的通过情况以重新生成的正式验收报告为准；测试替身、历史报告和 Windows 交叉编译都不等于 Windows 终端、DACL、命名管道或原生 OpenSSH 已实机通过。

## 1. 环境要求

| 工具 | 要求 | 用途 |
| --- | --- | --- |
| [Node.js](https://nodejs.org/) | 22 或以上，附带 npm | 运行 AutoGit |
| [Git](https://git-scm.com/) | 2.28 或以上 | 本地版本管理与远程同步 |
| OpenSSH | 兼容的 `ssh`、`ssh-keygen` | SSH 密钥和认证；Windows 可使用 Git for Windows 提供的工具 |
| [GitHub CLI（gh）](https://cli.github.com/) | 可选 | GitHub 建库、公钥上传、PR、Issue、Release 等 API 功能 |

普通 Git 操作不需要 gh；GitHub API 登录与 SSH 公钥授权是两件事。

## 2. 安装和启动

### 日常使用：只输入 autogit

完成一次安装后，在任意目录输入：

```sh
autogit
```

接下来按中文提示操作，无需先切到源码目录，也不必记目录参数：

1. 首次选择 **AutoGit 资料保存文件夹**，可直接回车接受默认位置；它不是项目代码目录。以后记住并显示位置，不重复询问。
2. 首次自行设置**独立的 AutoGit 解锁密码**并再次输入确认：至少 12 个字符、最多 1024 个 UTF-8 字节。只在无回显秘密输入中输入，不是系统密码、GitHub 密码、Token 或 SSH 私钥口令；请不要复用那些密码。两次输入有效且一致后才创建加密库和缺少的目录。
3. 首次将恢复码与资料目录分开、离线保管并确认；以后启动输入该库的解锁密码。密码错误时明确选择重试、恢复或退出；最多尝试 3 次后只能恢复或退出，不会自动覆盖、清空旧库。如果记住的位置消失，会引导找回或明确新建，不会静默用空库替代。
4. 每次选择本次项目：继续上次、当前目录、打开本地文件夹、创建新文件夹、下载远程项目，或从最近使用/收藏中选择。新建文件夹不会自动初始化 Git、提交或上传。
5. 进入任务菜单，选择保存、上传、获取代码等操作。没有账号时，下载引导中也能先新建/导入账号或录入加密 Token。

密码只通过交互式终端的无回显入口读取，不支持命令行参数、环境变量、普通 stdin 管道或配置文件传入密码。Linux 不需要 root、sudo 或安装 PAM，Windows 不需要管理员、系统账户密码或 Windows Hello。更换资料位置、修改解锁密码及立即锁定均在 **使用设置** 子菜单中完成。

### 一次性安装或更新本地 npm 包

只安装**本次源码验收重新生成、包含对应平台原生助手**的包。旧版同版本号归档不能因为源码改动而自动变成新包；先检查对应 `release` 报告和哈希，不要混用历史归档。

**Linux（当前用户可写的 npm prefix，不要使用 sudo）**：

```sh
npm install --global --prefix "$HOME/.local" ./artifacts/autogit-cn-0.5.0.tgz
export PATH="$HOME/.local/bin:$PATH"
autogit --version
autogit
```

把 `export PATH="$HOME/.local/bin:$PATH"` 加入自己的 shell 启动文件后，新终端也能直接使用。若已有 Node 版本管理器提供的用户级 prefix，可沿用它；不要为了权限错误改用 root 安装。

**Windows PowerShell（用户目录中的 npm prefix，不要以管理员身份运行）**：

```powershell
$prefix = Join-Path $env:LOCALAPPDATA "AutoGit\npm"
npm.cmd install --global --prefix "$prefix" .\artifacts\autogit-cn-0.5.0.tgz
$env:Path = "$prefix;$env:Path"
autogit.cmd --version
autogit.cmd
```

把上面的 `$prefix` 实际路径加入 Windows 的**用户 PATH** 后，新终端也可直接启动。Windows npm 启动脚本在 prefix 本身，Linux 则在 prefix 的 `bin/`；两者不要混用。如果执行策略阻止 `.ps1` 启动脚本，使用 `npm.cmd` / `autogit.cmd` 即可，无需放宽系统执行策略。

也可以把对应平台的包复制到其他机器，再用其实际路径安装。**目前没有发布到公共 npm registry**，不要直接安装 registry 上的同名包。`artifacts/` 是源码交付目录，不会随 npm 包安装到电脑上。

安装或更新只替换程序代码，不删除独立的 AutoGit 账号资料。安装后用 `autogit --version` 核对实际运行的版本；多个 Node/npm 环境可能各有一份安装。

### 从源码启动

在本项目目录执行：

```sh
npm ci --ignore-scripts
npm run build
npm run build:native   # 构建原生密钥/权限助手需 Go 1.26+，不安装 PAM 或系统认证策略
node dist/cli.js
```

每次启动都用所选凭据库的独立 AutoGit 密码解锁；不会调用 PAM、`LogonUserW` 或修改系统账户。解锁成功后才进入项目选择和任务菜单；退出或立即锁定会关闭本次凭据会话，不保留解锁状态。源代码构建和运行也不要求 root/管理员。

原生构建脚本只使用本地工具链和 `.claude-tmp/native-build/modules` 中的 Go 模块缓存，不自动下载工具链或依赖。首次开发可显式执行 `GOTOOLCHAIN=local GOMODCACHE="$PWD/.claude-tmp/native-build/modules" go -C native mod download` 准备已锁定模块（这是开发者自行选择的联网步骤）；Windows 将 `GOMODCACHE` 设置为同一项目缓存的绝对路径后，在 `native` 中执行 `go mod download`。CI 也单列此准备步骤；普通用户安装完整发行包不需要这些构建工具。

开发依赖只用于编译和测试。已有完整构建时也可使用 Linux `./start.sh` 或 Windows `start.bat`；两个启动器与 `autogit` 使用相同的首次位置选择/位置记忆流程，保留调用者的工作目录。便携资料目录请显式传 `--app-dir`，不再默认强制保存在程序旁边。

### 不必每次进入项目目录

```sh
# 在任意目录指定项目
autogit --path "/你的项目路径"

# 同时指定固定的个人资料根
autogit --app-dir "/你的 AutoGit 文件夹" --path "/你的项目路径"
```

这些是可选的高级参数，正常只输入 `autogit` 即可。不传 `--path` 时每次显示项目选择，上次项目和当前目录是快捷选项，不会静默替你选定。传 `--path` 只跳过项目选择，不跳过凭据库密码解锁。进入后仍可选择 **切换当前项目目录**，或用 **项目收藏与最近使用** 管理常用项目。

## 3. 第一次使用：账号、密钥和授权

1. 先选择持久的个人 **AutoGit 文件夹**，默认是主目录下的 `AutoGit`，再设置并确认独立的解锁密码。不要选在 `node_modules` 或 npx 缓存里。首次初始化会显示恢复码，请与资料目录分开离线保管。
2. 进入 **账号与资料 → 账号与密钥 → 新建账号 / 生成密钥**，填写标签、提交姓名、邮箱和预期 GitHub 登录名。
3. 本次解锁后的托管私钥加密保存，并由本次会话的独立 agent 提供；不再通过长期保存免口令明文私钥实现“记住认证”。旧版托管私钥需要确认迁移，外部原件不变。
4. 将公钥授权给 GitHub：可复制账号详情中的公钥，手工添加到 [SSH keys](https://github.com/settings/keys)；也可在 **GitHub 协作 → SSH 公钥授权** 中通过对应账号 Token 授权的 gh 上传所选 `.pub`。
5. 在账号管理中**绑定当前项目**；下载新的 SSH 项目时选好账号，下载成功后会绑定。
6. 测试账号并核对实际认证用户名。认证成功不代表对所有仓库都有写权限。

已有密钥可在账号管理中明确选择导入，软件在内存中解析并加密保存，不改外部原件；加密私钥的旧口令只在专用无回显提示中输入。Token 也只在 **HTTPS / GitHub 凭据** 子菜单的无回显入口输入，不要粘进普通菜单。录入不自动联网验证 Token，API 操作前仍会核验 actor。AutoGit 解锁密码不保存；它经 scrypt（N=32768、r=8、p=1）派生密钥包装随机数据密钥，凭据采用 AES-256-GCM。

**使用设置 → 修改 AutoGit 解锁密码** 会要求旧密码、新密码及再次确认，只更换本库的数据密钥包装，不修改系统或 GitHub 密码，也不关闭当前已解锁会话。新密码至少 12 个字符、最多 1024 个 UTF-8 字节；现有恢复码仍有效。

**使用设置 → 立即锁定并退出** 可结束本次凭据会话。忘记密码时，在启动解锁失败后明确选择**离线恢复码恢复**，输入恢复码后设置并确认新解锁密码；恢复成功会轮换恢复码，须重新离线保管。恢复码不是第二个日常登录密码。没有原密码或恢复码无法找回加密凭据，程序不会清空旧库。

**已有旧加密库**：仍可用当初包装该库的原密码解密，即使它曾是旧版要求的系统密码。这里仅解密旧库，不验证系统账户；解锁后立即在 **使用设置** 中改为独立 AutoGit 密码。修改操作系统密码不会自动改变库密码；原包装密码忘记时须用恢复码。旧明文托管私钥仍需明确确认迁移，外部密钥原件不变。

该保护不防同 UID/root 恶意进程、调试器或内存转储；旧明文备份和快照不会因迁移被自动擦除。

### 多账号和三种传输方式

例如建立“个人”“公司”两个账号，分别绑定项目 A、B。从 AutoGit 发起的提交和托管 SSH 操作会选择对应署名与密钥；**不修改 Git 全局身份，绑定也不会自动影响 IDE 或原生 Git**。只改账号的显示标签会保留项目绑定，不需要重新配置每个项目；真正改变署名或预期登录身份时会说明受影响绑定。

在 **账号与资料 → 主机 / SSH alias / 代理** 中选择：

| 模式 | 使用什么配置 |
| --- | --- |
| 托管 SSH | AutoGit 账号中的密钥，适合软件内管理多账号 |
| 原生 SSH | 本机已有 SSH config，可配合明确的 Host alias、代理或跳板 |
| HTTPS（托管） | 当前 AutoGit 会话的加密 Token；按 host / 仓库路径 / 账号限制，缺失时停止，不回退外部助手 |
| HTTPS（外部管理） | 仅在主机设置中明确选择；沿用外部 Git 凭据助手，不纳入 AutoGit 加密库 |

支持 GitHub.com、GitHub Enterprise 和普通 Git 服务。模式必须与实际远程 URL 一致；软件不会暗中改写远程地址。普通 Git 服务可以传输代码，但其专有 PR/Issue API 不属于 GitHub 功能。

## 4. 常用流程

### 下载已有项目

选择 **日常项目 → 下载已有项目 → 输入 Git SSH/HTTPS 地址 → 选择父目录与新文件夹 → 选择账号/传输配置。**

可使用新文件夹，也可选择已有空目录。名称无效或目录非空时，只重选文件夹名称，不必重填仓库地址和父目录。下载失败会说明原因；下载成功而绑定失败时保留目录，不自动删除已下载内容。

### 把本地项目第一次上传

选择 **日常项目 → 上传本地项目 → 新建 GitHub 仓库，或关联已有仓库 → 选择文件 → 填提交说明 → 上传。**

- 新建可选公开/私有。新仓库为空，不自动添加 README 或许可证；新初始化的本地分支使用 `main`。
- 自动建库需要可选 gh 工具，以及 **HTTPS / GitHub 凭据** 中录入的对应账号 Token；API 操作前核对实际 actor，不执行全局 gh 登录/切换。没有 gh 时，也可在 [GitHub 网页建库](https://github.com/new) 后关联地址。
- 已有远程可以保留，也可选择新的远程名称；不覆盖已有 `origin` 或悄悄改变拉取上游。
- 创建、关联、提交、上传分步报告。建库结果未知时先去 GitHub 核对，**不要直接重复建库**；已建成但关联失败时改用“关联已有仓库”。

### 每天保存和同步

| 想做什么 | 选择的动作 |
| --- | --- |
| 选择文件、提交并上传 | **保存修改并上传** |
| 只提交到本地，不联网 | **仅保存到本地** |
| 本地已经提交，只需上传 | **仅上传已有提交** |
| 获取远程更新 | **获取远程最新代码**（仅快进） |
| 查看修改、暂存差异和历史 | **查看与诊断 → 查看状态、差异和只读历史** |

已有暂存会明确显示，部分暂存不会被整个文件的其他修改替换。保存前，AutoGit 默认会把**超过 50 MiB 的全新未跟踪普通文件**加入项目根目录 `.gitignore`，文件仍保留在磁盘，不会自动暂存、删除或接入 Git LFS；50 MiB 正好不触发。规则写入后只有你明确选择 `.gitignore` 才会进入提交。已经跟踪、已暂存或部分暂存的文件不会被这个规则暗改；无法安全表示的特殊文件名只从本次提交候选中排除并提示。上传失败时保留本地提交，检查后重试上传即可，不必重复提交。

获取更新仅执行快进（`ff-only`）；工作区有改动、冲突、进行中的 Git 操作或历史分叉时停止，不自动 stash、merge、rebase 或中止操作。本地复杂状态须在外部 Git 工具处理后再回来重试；强推不是解决本地分叉或冲突的替代步骤。

### 远程管理与只读检查

远程管理保留 URL 查看与编辑、独立 fetch、为**当前分支**设置上游、远端分支删除，以及明确选择 `force-with-lease` 或无条件 `--force`。上游配置不创建或切换本地分支，普通上传失败不会自动变成强推。远端强推、删除等写入先展示目标与影响，再确认一次，不强制先 stash 或备份。

状态与历史入口保留差异、近期提交、历史分页、搜索、详情和历史图；它们是只读检查，不提供 reflog 恢复分支或本地历史改写。

**有意移除**：本地分支新建/切换/跟踪/改名/删除、手动 merge 与冲突处理、stash、取消暂存/文件还原工具、reset、clean、revert、cherry-pick、rebase、bisect 及其继续/跳过/中止、reflog 恢复分支、PR 本地 checkout、worktree、子模块和 Git LFS 管理。这是功能裁剪，不是藏在“高级模式”中；不会删除仓库已有的分支、stash、多工作区、子模块、LFS 对象或历史。只读状态检测及拒绝覆盖保护继续保留。

## 5. 六组任务菜单

主菜单只显示六组任务，先选分组，再按名称选择具体动作；子菜单编号以当前屏幕为准，不沿用旧版的独立功能编号。

| 分组 | 子菜单与动作 |
| --- | --- |
| 日常项目 | 下载已有项目、上传本地项目（新建或关联）、保存修改并上传、获取远程最新代码（仅快进）、仅保存到本地、仅上传已有提交 |
| 远程传输 | 远程地址管理、添加/改名/移除远程、仅上传、lease/无条件强推、删除远程分支、独立 fetch、设置当前分支上游 |
| GitHub 协作 | 仓库/组织/fork/权限、公钥授权、PR/Review/服务端合并、Issue、Tags/Releases/附件 |
| 账号与资料 | 账号与密钥、HTTPS / GitHub 凭据、主机 / SSH alias / 代理、使用设置、资料备份/恢复/搬迁、首次配置与依赖指引 |
| 项目管理 | 切换项目目录、收藏与最近项目、模板（.gitignore / README / 许可证） |
| 查看与诊断 | 状态/差异/只读历史、配置诊断 |

每个子菜单均可返回，主菜单可退出。模板、主机和备份分别放在项目管理或账号与资料中，不再提供独立的高级项目工具列表。

默认是**快捷模式**，日常操作不重复确认；在 **使用设置** 子菜单可改为详细模式。`:q` 返回，文件选择支持 `1,3` / `1 3`，`a` 全选。取消不会撤销前面已经完成的步骤。原生 Git/SSH 的输出可能是英文。

GitHub 协作保留组织建库、fork、PR 评论/Review/**服务端合并**、Issue 编辑、标签和 Release 附件、协作者/团队权限。PR 的 merge/squash/rebase 是服务器策略，不执行本地 merge/rebase；不再提供 PR 本地 checkout。本地标签准备、单标签上传与删除仍属于发布流程。Release 附件保存重名时可换名或明确覆盖，覆盖前确认一次，下载失败不先删原文件。普通下载和新建本地 Tag 在快捷模式下直接执行，不套远程写入确认。权限、分支保护和 SSO 等仍按服务器规则执行。

## 6. 账号资料在哪里，怎么备份

```text
你选择的 AutoGit/
└── data/
    ├── vault.json      加密凭据库（独立 AutoGit 密码包装数据密钥，恢复码不在这里）
    ├── profiles/       账号元数据、密文引用和公钥
    ├── bindings.json   项目与账号的绑定
    ├── projects.json   项目收藏和最近使用
    ├── hosts.json      项目主机和传输配置
    ├── known_hosts     已确认的 SSH 主机指纹
    └── settings.json   偏好和上次项目
```

文件按需生成。npm 更新、卸载或清理 npx 缓存不会删除这份独立资料。

普通启动用一份**只含资料根路径**的 `location.json` 记住位置：Linux 为 `${XDG_CONFIG_HOME:-~/.config}/autogit/location.json`，Windows 为 `%APPDATA%\AutoGit\location.json`。显式 `--app-dir` 不读写这个指针；优先级是 **`--app-dir` > `AUTOGIT_DATA_DIR` > 位置指针 / 首次选择**。环境变量指向实际 `data`，参数指向它的父文件夹。

- **使用设置 → 切换资料根**只切换位置，不复制或删除旧资料。已有目标库使用它自己的独立密码解锁；没有可用资料时须明确确认新建，不自动把错误密码当成空库。
- **账号与资料 → 资料备份 / 恢复 / 搬迁**用于真正的备份与迁移；搬迁默认保留来源。
- 新会话备份是 `manifest.json + files/`：秘密已在 `vault.json` 中加密，公钥和普通元数据仍可读；SHA-256 只校验复制完整性，不是加密。交互恢复在 staging 输入**备份库自己的密码**、验证解密及资料结构，成功后才替换/切换目标，不重复索取密码。不带交互输入的底层恢复只能用当前存活会话的同一 DEK 验证其副本，不能跳过独立密文库的解锁。
- 托管 Token 在库中加密，并包含在密文备份中；恢复码、AutoGit 解锁密码、明文 DEK、agent/IPC 不包含在备份中。外部 SSH/helper/gh 的凭据及缓存不纳入备份，退出 AutoGit 不清除它们。旧版明文私钥备份仍可能泄露秘密，需在恢复向导中迁移。
- 兼容原有 profiles/bindings schema 2、settings schema 1。项目移动后请明确映射旧路径到新路径，不按同名目录猜绑定。

**请勿分享或公开上传整个资料文件夹。**加密不能防止离线猜测弱解锁密码，元数据也未隐藏。泄露时请在平台撤销对应公钥/Token，再替换凭据；只删除本地文件不能撤销远端权限。共用一份资料就是共用其中的账号，需要独立身份时使用不同资料根。

## 7. 常见问题

**明明绑定了账号，为什么还是认证失败？** 先检查实际远程 URL 与传输模式。托管 HTTPS 需要在 **HTTPS / GitHub 凭据** 子菜单录入对应 host / 账号 Token，并按项目绑定；缺失时不会回退外部助手。若明确选择外部 HTTPS，则由外部工具负责缓存。托管 SSH 还需公钥已授权、账号有仓库权限。可用 **检查配置和诊断问题** 检查。

**为什么 GitHub 能登录，SSH 仍不能上传？** gh API 登录不等于公钥已授权，公钥授权也不等于仓库写权限。组织 SSO 和分支保护同样可能限制操作。

**为什么拉取没有自动合并？** 普通获取更新只快进。历史分叉、冲突或进行中的操作请在外部 Git 工具处理；本版不再提供本地合并、变基或冲突恢复入口，也不会建议用强推代替本地处理。

**上传失败，刚才的提交还在吗？** 在。选择 **仅上传已有提交** 重试上传。若提示远端已成功但上游关联未完成，只需检查本地上游配置，不要重复建库或强推。

**生成 README、忽略规则会自动提交吗？** 不会。大文件规则会在 **上传本地项目 / 保存修改并上传 / 仅保存到本地** 的提交准备阶段自动追加，取消后续提交也会保留已写入的规则，但不会擅自暂存。若 `.gitignore` 不可写或子目录规则重新包含大文件，会说明原因并仅跳过对应大文件，其他文件仍可保存。停止跟踪只调整 index，不删除工作区原文件；忽略规则不能从已有历史中抹去内容。

**把程序文件夹搬走会丢账号吗？** npm 程序和个人资料是分开的；两个启动器默认都使用首次选择并记住的位置，不再强制使用旁边的 `data/`。移动资料请用备份/搬迁工具，或显式指定新的 `--app-dir`。跨系统时可能需要重新选择 SSH 程序路径。

## 8. 项目结构与开发验证

```text
src/                 TypeScript 源码
tests-node/          Node 内置测试与隔离 fixture
scripts/             构建、临时目录和正式验收工具
docs/capabilities.md 完整功能台账与验收边界
.github/workflows/   跨平台 CI 配置
dist/                生成的运行文件
artifacts/           当前版本包与一套正式验收证据
.claude-tmp/         自动隔离的测试临时目录
start.sh / start.bat 便携启动器
```

```sh
npm run typecheck
npm test
npm run verify
```

`npm test` 会先构建，再运行全部测试。`npm run verify` 是本地发行包验收入口：核对原生密钥/权限 helper、离线安装开发依赖、类型检查、全套测试、生产 CLI 的终端/解锁门禁及独立密码 PTY 交互、代码级解锁替身驱动的旧工作流交互、本地打包、tar 内容白名单与源码快照核对。替身工作流只证明菜单/Git 行为，不能代替生产密码解锁验收；PTY 证据也只适用于实际运行的平台。首次运行须已通过 `npm ci --ignore-scripts` 准备好 npm 缓存，离线依赖不足时不会自动改用联网安装。

验收成功后，`artifacts/` 更新当前版本的 8 项正式文件：安装包、`release` JSON、`verification` 摘要、全套测试日志、类型检查、npm-ci、纯 JSON 的 npm-pack 记录和汇总 CLI 转录。测试临时目录成功后自动清理；失败的正式验收会显示保留的诊断位置，不把半套结果标为通过。

测试使用隔离 HOME、Git、gh、资料根与 npm 环境；以真实本地仓库/bare remote 和 fake gh 验证流程，不读取个人密钥，不连接真实 GitHub。npm 生命周期测试覆盖隔离安装、重装、卸载与离线执行后的资料保留。

**实际验收与适用范围分开记录**：裁剪版须以当前源码重新生成的 `artifacts/verification-0.5.0.txt` 和 `release-0.5.0.json` 为准，旧同版本报告不能证明新菜单和退役文件缺失已通过。CI 包含 Ubuntu/Windows × Node 22/24，但配置存在不等于全部已运行通过；Windows 原生终端/OpenSSH、Node 24、真实 GitHub/Enterprise 和 SSH 代理/跳板仍需分别实测。Git LFS 管理已移除，不再列作待验收能力。更多范围与限制见 [功能与缺口台账](docs/capabilities.md)。
